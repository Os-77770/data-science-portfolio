# PostgreSQL Customer Analytics

I built this project to get hands-on with a real PostgreSQL database end
to end: designing a warehouse schema, loading it efficiently, checking
the load reconciles, and writing the kind of analytical SQL a data team
runs every week — CTEs, window functions, segmentation and cohort
analysis — against **PostgreSQL 16**.

> **Data honesty note:** The dataset is **100% synthetic** — the same
> generated telco customer dataset I use in my churn-analytics project
> (8,000 customers, fixed seed 42, generated by `src/generate_data.py`).
> No real customer data is used. Every number below is a real output of
> running the SQL in this repo against the loaded database.

---

## Business questions

1. Which customer segments churn the most? (contract × tenure)
2. How is monthly revenue trending, and who are the most valuable
   customers in each segment?
3. Do signup cohorts differ in quality — churn and lifetime value?
4. Which *currently active* customers look riskiest right now?

## Schema

I reshaped the flat customer file into a small star-style warehouse.
The dataset is a snapshot as of 2024-12-01: a customer's signup month is
the snapshot month minus (tenure − 1) months, and monthly billing runs
from signup through the snapshot (each month billed at the customer's
monthly charge ±3%, the convention the source dataset uses for totals).

```
customers                                  subscriptions
  customer_id        PK                      subscription_id  PK
  senior_citizen     BOOLEAN                 customer_id      FK -> customers
  paperless_billing  BOOLEAN                 contract_type    TEXT
  payment_method     TEXT                    internet_service TEXT
  tenure_months      INTEGER                 monthly_charges  NUMERIC(10,2)
  support_calls      INTEGER                 total_charges    NUMERIC(12,2)
  late_payments      INTEGER
  signup_month       DATE
  churned            BOOLEAN

monthly_billing  (fact table, 241,609 rows)
  customer_id          FK -> customers  ┐
  billing_month        DATE             ┘ composite PK
  months_since_signup  INTEGER
  amount               NUMERIC(10,2)
```

Row counts after load: `customers` 8,000 · `subscriptions` 8,000 ·
`monthly_billing` 241,609. Indexes support the actual query patterns:
signup month (cohorts), billing month (revenue scans), contract type
(segmentation), and (customer, months_since_signup) on the fact table.
The composite primary key already serves per-customer lookups —
`EXPLAIN ANALYZE` for one customer's full billing history picks an
Index Scan on the PK and runs in ~0.2 ms.

## The queries (`sql/`)

| File | Techniques | Answers |
|---|---|---|
| `02_churn_by_segment.sql` | CTEs, CASE banding, conditional aggregation, `RANK()` | Churn rate by contract × tenure band |
| `03_window_functions.sql` | `LAG()` MoM change, running totals, 3-month moving average, `ROW_NUMBER()` top-N per segment | Revenue trend; top 5 customers per contract |
| `04_cohort_retention.sql` | Cohort grouping by signup quarter, lifetime-value joins | Cohort churn + revenue per customer |
| `05_risk_segments.sql` | Behaviour banding, `NTILE()` | Churn by support calls × late payments; active high-risk watchlist |

A note on method for query 04: a snapshot has no churn *event dates*, so
a classic retention triangle / survival curve would be fake precision.
I run the cohort analysis the data supports and state the confound
(newer cohorts churn more mostly because they are younger — and young
customers churn more) right in the SQL comments.

## Findings (real query outputs)

- **Overall churn: 30.21%.** Worst segment: **month-to-month, 0–6 months
  tenure — 62.35% churn**. Safest: **two-year contracts at 49+ months —
  3.69%**. For every contract type, churn falls steadily with tenure.
- **Revenue:** $14,483,269.68 billed across 72 months; the base grows
  from 422 active customers (Jan 2019, $26,234.95) to 8,000 (Dec 2024,
  $475,983.85). The top month-to-month customer by lifetime value billed
  $8,149.12 over 72 months.
- **Cohorts:** the 2019-Q1 cohort churned at 7.47% with $4,453.09
  lifetime revenue per customer; the 2024-Q4 cohort shows 61.47% — read
  with the tenure confound above, not as "customers got worse."
  Inside every cohort, month-to-month is still the worst contract.
- **Behaviour risk:** customers with 5+ support calls and 3+ late
  payments churned at 58.33%; the cleanest bucket (0 calls, 0 late
  payments) at 18.22%. Query 05 also produces a 15-customer watchlist of
  still-active customers in the riskiest behaviour bands.

Full outputs, CSVs and charts are in `outputs/`
(`analysis_summary.txt`, `analysis_run_log.txt`, three PNG charts).

## How to run

```bash
# PostgreSQL 16 (Debian/Ubuntu):
sudo apt-get install postgresql
sudo pg_ctlcluster 16 main start

python3 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt

python src/generate_data.py   # data/customers.csv (synthetic, seed 42)
python src/build_tables.py    # reshape into warehouse CSVs
python src/setup_db.py        # create db + role, schema, COPY load
python src/checks.py          # reconciliation checks (all must PASS)
python src/run_analysis.py    # run sql/*.sql, save outputs + charts
```

The database (`customer_analytics`) and role are created by
`setup_db.py`; the credentials in `src/pgutil.py` are throwaway
local-development values. Queries can also be run directly in `psql`
against the `.sql` files.
