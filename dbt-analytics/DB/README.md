# dbt Analytics Engineering — Customer Churn Warehouse

I built this project to practice analytics engineering the way it is done
on a data team: raw data lands untouched, and all cleaning, typing,
testing and business logic lives in version-controlled SQL models built
with **dbt Core** on a **DuckDB** warehouse.

> **Data honesty note:** The dataset is **100% synthetic** — the same
> generated telco customer dataset I use in my churn-analytics project
> (8,000 customers, fixed seed 42, generated by `src/generate_data.py`).
> No real customer data is used. Every number below is a real output of
> running `dbt build` on that data in this repo.

---

## What questions the warehouse answers

- Which customer segments churn the most? (`mart_churn_segments`)
- What does the business look like month by month — revenue, active
  customers, new signups, churn? (`mart_monthly_metrics`)

## How the data is shaped

Starting from one flat customer file, I first reshape it into a small
warehouse layout (customers / subscriptions / monthly billing, one row
per customer per active month — 241,609 billing rows), then model it in
dbt in three layers:

```
raw (DuckDB tables, all values as strings, loaded by src/load_raw.py)
  raw_customers          8,000 rows
  raw_subscriptions      8,000 rows
  raw_monthly_billing    241,609 rows
        |
        v
staging (views — typing, renaming, 1:1 with sources)
  stg_customers
  stg_subscriptions
  stg_monthly_billing
        |
        v
intermediate (view — reusable joins and derived fields)
  int_customer_monthly   billing + customer + plan, tenure band, signup quarter
        |
        v
marts (tables — business-ready aggregates)
  mart_churn_segments    churn by contract type x tenure band
  mart_monthly_metrics   monthly scorecard: revenue, actives, signups, churn
```

The raw layer is deliberately untyped (every column lands as a string,
the way an ingestion tool would land it). Casting and renaming happen
only in staging, so downstream models never have to care what the source
files looked like.

## Testing

`dbt build` runs **22 data tests** alongside the 6 models, and the whole
build is green (`PASS=28 WARN=0 ERROR=0`, full log in
`outputs/dbt_build_output.txt`):

- `unique` + `not_null` on primary keys (staging models, mart grains)
- `accepted_values` on contract type and internet service
- `relationships` from subscriptions/billing back to customers
  (no orphan foreign keys)
- documented columns in `schema.yml` files for every model
- a singular test (`tests/assert_billing_grain_unique.sql`) asserting
  the billing grain: exactly one row per customer per month

## Findings (real outputs)

- **Overall churn: 30.2%** of the 8,000 customers.
- The worst segment is **month-to-month contracts in their first 6
  months: 62.35% churn** (159 of 255 customers). The safest is
  **two-year contracts at 49+ months: 3.69%**.
- Every contract type shows the same shape: churn is worst early and
  falls steadily with tenure — the first year is where retention work
  pays off.
- The monthly scorecard covers **72 months (Jan 2019 – Dec 2024)** and
  **$14,483,269.68** in total billed revenue; Dec 2024 billed
  $475,983.85 across all 8,000 customers.
- One modelling note I was careful about: this is a *snapshot* dataset.
  Every customer's observed billing window ends at the Dec 2024
  snapshot, so in `mart_monthly_metrics` the churned customers' final
  billing month is the snapshot month. The monthly churn column is
  therefore not a churn time series — I kept it because it makes the
  snapshot semantics visible instead of hiding them.

## How to run

```bash
python3 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt

python src/generate_data.py   # data/customers.csv (synthetic, seed 42)
python src/build_tables.py    # reshape into warehouse CSVs
python src/load_raw.py        # land raw_* tables in warehouse.duckdb
dbt build --profiles-dir .    # build all models + run all tests
```

Inspect the results with any DuckDB client, e.g.
`select * from mart_churn_segments;` against `warehouse.duckdb`.

## Files

| Path | What it is |
|---|---|
| `dbt_project.yml` | Project config; layer materializations (staging/intermediate = views, marts = tables) |
| `profiles.yml` | DuckDB connection profile |
| `models/staging/` | Staging models + `_sources.yml` + schema/tests |
| `models/intermediate/` | `int_customer_monthly` |
| `models/marts/` | The two marts + schema/tests |
| `tests/` | Singular SQL test for the billing grain |
| `src/` | Data generation, warehouse reshaping, raw loader |
| `outputs/` | Captured full green `dbt build` log + the two marts exported as CSVs |
